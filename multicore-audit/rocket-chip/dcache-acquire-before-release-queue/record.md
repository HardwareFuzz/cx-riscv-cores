## Failure mechanism

At the affected parent, the DCache has a C-channel release queue, but the queue does not expose an empty-status signal to cached miss admission. Cached miss admission is instead controlled by `release_ack_wait` alone:

```scala
val s2_valid_miss =
  s2_valid_masked && s2_readwrite &&
  !s2_meta_error && !s2_hit && !release_ack_wait
```

A dirty Probe response can place release traffic in that C-channel queue. If the queued release traffic is still blocked, the DCache can accept a new cached miss because `release_ack_wait` is clear even though the release queue is nonempty. The new miss emits an Acquire while the earlier C-channel release remains unable to make progress. At the shared coherence manager, the blocked C traffic can prevent the D-channel response required by the new Acquire from progressing. The resulting dependency can hold both transactions and produce a coherence progress deadlock.

This is a control defect in the interaction between cached miss admission, the DCache release queue, and the shared TileLink coherence channels. The failure is not a property of a particular memory value: legal C-channel backpressure combined with the queue state is sufficient to create the blocked ordering.

## Necessary multi-client trigger

The trigger requires a shared coherent fabric with at least two cache clients or harts. One peer cache issues a dirty Probe to the affected hart, causing the affected DCache to enqueue a dirty release response on C. While that release response remains queued or backpressured, the affected hart performs a cached miss whose Acquire is admitted by the old `!release_ack_wait` test. The peer/coherence manager and the affected DCache then participate in the blocked C-versus-D transaction dependency.

The multi-client condition matters because the dirty Probe and its release response are generated by a distinct coherent cache client. This is a shared DCache coherence ordering/progress failure, not a local uncached request-path issue.

## Canonical fix and closure

Direct fix [`3cbc5262ecf342314896519a699d1bf9cad0dee4`](https://github.com/chipsalliance/rocket-chip/commit/3cbc5262ecf342314896519a699d1bf9cad0dee4) adds the release-queue empty status and derives the admission predicate:

```scala
val can_acquire_before_release =
  !release_ack_wait && release_queue_empty
```

The cached miss and data-error paths are gated by this predicate, so a new Acquire is not admitted while earlier release traffic remains in the release queue. The fix was merged in [PR #955](https://github.com/chipsalliance/rocket-chip/pull/955) as [`e945f6e2656239308dc2c0dadc9e3ffc32969bdb`](https://github.com/chipsalliance/rocket-chip/commit/e945f6e2656239308dc2c0dadc9e3ffc32969bdb), and the corrected implementation is present in canonical master [`55bcad0f59436de98ea510334121de8546b9e9d7`](https://github.com/chipsalliance/rocket-chip/commit/55bcad0f59436de98ea510334121de8546b9e9d7).

The finding is distinct from the later Rocket DCache ReleaseAck/Acquire/ProbeAck issue: this record concerns the older `acquireBeforeRelease` release-queue-drain omission and its direct queue-empty admission fix.
