## Failure mechanism

The affected DCache tracked a voluntary ReleaseAck:

```scala
val release_ack_wait = Reg(init = Bool(false))
```

It set that state after the first C-channel Release beat and cleared it
when the D-channel ReleaseAck arrived. The Probe blocking predicate did not
include this state:

```scala
val block_probe =
  releaseInFlight ||
  grantInProgress ||
  blockProbeAfterGrantCount > 0 ||
  lrscValid
```

There was therefore a reachable window in which the Release burst had
finished, `releaseInFlight` was clear, and `release_ack_wait` was still true.
The DCache could accept a B-channel Probe before the ReleaseAck that closed
the outstanding voluntary Release. On a non-FIFO C/D/B channel ordering,
this could expose stale coherence state or data.

## Necessary multi-client trigger

1. Hart A starts a voluntary eviction or flush and emits a C-channel
   Release/ReleaseData.
2. Hart A waits for the manager's ReleaseAck.
3. Hart B requests the same line or another conflicting ownership transition.
4. The coherence manager sends a Probe to Hart A before the ReleaseAck
   arrives.
5. The affected DCache accepts the Probe during the pending-ReleaseAck
   window, violating the required ordering.

The Probe is generated by an independent coherent client; it is not a local
single-cache request sequence.

## Canonical fix and closure

PR #1999 records the Release address and uses an address-qualified pending
ReleaseAck block:

```scala
val release_ack_addr = Reg(UInt(paddrBits.W))

val block_probe_for_pending_release_ack =
  release_ack_wait &&
  (tl_out.b.bits.address ^ release_ack_addr)(idxMSB, idxLSB) === 0
```

The final PR refinement narrows the block to the relevant cache-set index,
preserving ordering while limiting unrelated Probe stalls. The complete
closure is `df0e7a9c -> 724f73fb -> 0a4edb61`; PR #1999 is merged and the
exact affected parent is `50750dc6985246b701265d365813fc3fb747e360`.
